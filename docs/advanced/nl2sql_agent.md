# 🧠 高级实战：NL2SQL 数据问答 Agent

> 让不会写 SQL 的人，用一句中文把数据库问明白。代码：`projects_advanced/nl2sql_agent/`
>
> 这是一个「教学但偏生产」的项目：重点不在于跑通 Demo，而在于讲清把 LLM 接到数据库上时
> 真正要解决的两个工程问题——**安全（只读护栏）** 与 **鲁棒（错误自愈）**。

---

## 一、需求与方案设计

### 1.1 业务诉求

运营、老板、产品经理天天有数据问题：「上个月哪个城市卖得最好？」「哪个商品销售额最高？」。
传统链路是「提需求 → 排期 → 数据分析师写 SQL → 出图」，慢且贵。
我们想要的是：**用户说人话，系统自己翻译成 SQL 并答出来**——这就是 NL2SQL（自然语言转 SQL）。

### 1.2 为什么用 Agent，而不是「一把梭让模型直接输出 SQL」

最朴素的做法是：把表结构塞进 Prompt，让模型一次性吐出 SQL 再执行。问题有三：

- **模型不知道真实结构**：表多、列多时塞不下，也容易拼错字段名。
- **一次写错就没救**：SQL 报错后没有「再来一次」的机制。
- **安全无从谈起**：模型可能生成 `DROP TABLE`。

Agent（ReAct 模式）天然解决前两点：它能**多步**地「先看表 → 再看列 → 写 SQL → 跑 → 错了再改」，
把探查和纠错拆成多轮工具调用。安全则由我们在工具内部加护栏来兜底。

### 1.3 架构总览

```
用户问题（自然语言）
      │
      ▼
┌─────────────────────────────────────────┐
│  create_react_agent（LangGraph 编排）     │
│  System Prompt：先 list_tables → get_schema │
│                → 写 SELECT → run_sql → 自愈 │
└───────┬───────────┬───────────┬───────────┘
        │           │           │
   list_tables  get_schema   run_sql ← 只读护栏 + 错误回传
        └───────────┴───────────┴──► SQLite（shop.db，只读访问）
```

三张表：`customers` / `products` / `orders`，外键关联，金额 = 单价 × 数量。

## 二、实现详解

### 2.1 三个工具：探查 + 执行

| 工具 | 职责 | 设计要点 |
| --- | --- | --- |
| `list_tables()` | 列出所有表名 | 让模型「先知道有哪些表」，而非凭空猜 |
| `get_schema(table)` | 返回某表列定义 | 先校验表是否存在，不存在则**把可用表名列回去**，引导模型纠正 |
| `run_sql(sql)` | 执行只读查询 | 护栏 + 截断 + 错误回传，下面细讲 |

每个工具的 docstring 都写明「什么时候该用我」——这是 ReAct Agent 选工具的唯一依据，必须写清楚。

### 2.2 重点一：只读护栏（Read-only Guardrail）

让模型生成的 SQL 直连数据库，最大的风险是**写操作**（删表、改数据）。我们用**双层防御**：

```python
# 第 1 层：必须以 SELECT 或 WITH（CTE 也是只读）开头
head = cleaned.lstrip("(").lstrip()
if not re.match(r"(?i)^(SELECT|WITH)\b", head):
    return "拒绝执行：只允许 SELECT 查询……"

# 第 2 层：全句扫描写操作关键字黑名单
hit = _FORBIDDEN_RE.search(cleaned)   # INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/...
if hit:
    return f"拒绝执行：检测到写操作关键字 '{hit.group(1)}'……"
```

设计取舍：白名单（开头必须 SELECT/WITH）+ 黑名单（禁写关键字）双管齐下，单靠开头判断挡不住
`SELECT ...; DROP TABLE ...` 这种「拖尾注入」；用词边界 `\b` 匹配避免误杀含关键字字母的列名
（如 `created_at` 不会被当成 `CREATE`）；拒绝时返回「人话」而非抛异常，模型看到提示会自己改写。

> 生产加固方向（文末复盘展开）：除了关键字过滤，更稳的是**用只读数据库账号 / 只读连接**，
> 从权限层面根除写操作，关键字过滤只作为第一道闸。

### 2.3 重点二：错误自愈（Self-healing）

NL2SQL 第一次写对的概率并不高（列名记错、聚合函数用错、日期格式不对）。
让 Agent 能自愈的**唯一秘诀**：SQL 报错时，**把数据库的真实错误原样喂回给模型**。

```python
except sqlite3.Error as e:
    # 不要 try/except 后吞掉错误！原样回传，模型才知道哪里错了
    return f"SQL 执行出错：{e}。请检查表名/列名是否正确，修正后重试。"
```

配合 System Prompt 里那句「如果 run_sql 返回报错，仔细读错误，修正 SQL 后重试，不要放弃」，
ReAct 循环就会自动再走一轮：读错误 → 改 SQL → 重跑。这就是「自愈」的全部机制——
**不是模型有多聪明，而是我们把纠错所需的信息完整地还给了它**。

常见自愈案例：`no such column: total` → 模型改用真实列名 `amount`；`near "GROUP": syntax error`
→ 模型修正语法。

### 2.4 结果截断与可观测性

- **截断**：`fetchmany(MAX_ROWS + 1)`，多取一行用来判断是否被截断；超量时提示「请加 LIMIT
  或聚合」。防止 `SELECT *` 把大表怼进上下文，既烧 token 又慢。
- **可观测**：`ask()` 遍历 `result["messages"]`，把每次 `tool_calls`（工具名 + 参数）和
  `ToolMessage`（返回预览）打印出来。调试 Agent「为什么这么答」全靠这条轨迹。

### 2.5 System Prompt 的作用

Prompt 里把**正确工作流**写死（先 list_tables → 再 get_schema → 写 SELECT → 出错重试），
并重申只读约束与「结论必须来自真实返回、严禁编造」。Prompt 不是越长越好，而是要把
「容易犯的错」提前堵住——这比事后纠错成本低得多。

## 四、复盘与进阶

| 维度 | 当前实现 | 生产加固方向 |
| --- | --- | --- |
| 安全 | 关键字黑名单 + SELECT 白名单 | 改用**只读数据库账号/只读连接**从权限层根除写操作；限制可访问的表 |
| 性能 | 单次 50 行截断 | 自动给无 LIMIT 的查询追加 `LIMIT`；超时熔断；连接池 |
| 准确率 | Schema 全量喂给模型 | 表多时做 **schema 检索**（只喂相关表）；加 few-shot 示例；列注释/枚举值采样 |
| 体验 | 一问一答 | 加 checkpointer 支持多轮追问；流式输出 SQL 与结果 |
| 可信 | 直接返回答案 | 把生成的 SQL 一并展示给用户**审计**；高风险查询走人工确认（HITL） |
| 评测 | 人工看结果 | 建「问题→标准答案」评测集，自动跑执行准确率（Execution Accuracy） |

进阶练习建议：给 `run_sql` 加自动追加 LIMIT；表多时新增 `search_tables(keyword)` 做 schema 检索；
接 `MemorySaver` + `thread_id` 支持追问；把最终 SQL 回显给用户做成可审计形式。

## 五、面试怎么考

**Q1：怎么防止 NL2SQL 的 Agent 把数据库删了 / 改了？**
A：核心是**最小权限 + 多层护栏**。最稳的是给 Agent 一个**只读数据库账号/只读连接**，
从权限层根除写操作；在应用层再加 SQL 白名单（必须 SELECT/WITH 开头）+ 写关键字黑名单
（全句扫描，挡拖尾注入）双重过滤。本项目演示了应用层这层，生产应叠加权限层。

**Q2：模型 SQL 写错了怎么办？为什么你的 Agent 能自己改对？**
A：关键不在模型多强，而在**把数据库的真实报错原样回传**给模型，并在 System Prompt 里
指示「读错误、改 SQL、重试」。ReAct 循环据此自动再走一轮。如果把异常 try/except 吞掉，
自愈就失效了——错误信息是模型纠错的唯一线索。

**Q3：为什么不直接让模型一次输出 SQL，而要做成多步 Agent？**
A：一次输出无法**探查真实结构**（表/列多时塞不下、易拼错）、也无法**纠错重试**。
Agent 把「看表 → 看列 → 写 → 跑 → 改」拆成多轮工具调用，准确率和鲁棒性都更高。

**Q4：表非常多、列非常多，Schema 塞不进上下文怎么办？**
A：做 **schema linking / 检索**：先用一个工具按关键词检索出可能相关的表，只把这几张表的
结构喂给模型，而不是全量。还可以给列加注释、采样枚举值，帮模型选对字段。

**Q5：怎么评估 NL2SQL 系统好不好？**
A：常用 **执行准确率（Execution Accuracy）**——生成 SQL 执行后的结果是否等于标准答案的结果
（比纯文本比对 SQL 更合理，因为同一问题可有多种等价写法）。建「问题→标准结果」评测集自动回归。

**Q6：`temperature` 为什么设 0？**
A：SQL 生成是「有标准答案」的确定性任务，0 温度让输出最稳定、可复现，减少随机性导致的
字段名漂移或语法抖动。Agent 工具选择同理，也建议 0。
