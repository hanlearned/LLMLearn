# 项目 3：GraphRAG 原型系统

> 前沿加分项。当问题需要「跨多个片段串联关系」时，普通向量 RAG 力不从心，GraphRAG 用知识图谱补上这块短板。面试里能讲清 GraphRAG 的动机和原理，是区分「会用 RAG」和「懂 RAG」的分水岭。
>
> 代码：`stage02_rag/project03_graphrag/graphrag.py`（零额外依赖，可直接跑）

---

## 一、为什么需要 GraphRAG

普通向量 RAG 检索的是「**语义相似的片段**」。它擅长「员工年假几天？」这类答案集中在单个片段的问题，但面对**关系型/多跳问题**就露怯：

> 「和报销审批相关的角色，分别还负责哪些事？」

这个问题的答案散落在多个片段（报销要部门负责人审批、负责人还管请假审批…），它们之间靠「角色」这个实体串联，但彼此**语义并不相似**，向量检索凑不齐。

**GraphRAG 的解法**：先把文档抽成知识图谱（实体是点、关系是边），提问时定位实体，再**沿着图的边把关联事实捞出来**，一起喂给 LLM。

---

## 二、方案设计：三步流水线

```
文档 ──抽取──> (主体,关系,客体) 三元组 ──建图──> 知识图谱(邻接表)
                                                      │
问题 ──找实体──> 命中实体 ──取邻居子图──> 关系事实 ──喂给 LLM──> 答案
```

| 步骤 | 做什么 | 关键技术 |
|------|--------|---------|
| 抽取 Extract | 让 LLM 从每个 chunk 抽三元组 | `with_structured_output(TripleList)` 强约束输出 |
| 建图 Build | 三元组组装成邻接表 | 无向存储，便于双向检索 |
| 问答 Query | 定位实体→取一跳邻居→生成 | 子图作为上下文 |

> 本原型用**邻接表 dict** 而非 networkx，零依赖、看得清原理。生产级 GraphRAG（如微软 GraphRAG）还会做**社区聚类**和**多跳推理**，但内核就是这三步。

## 三、实现详解

### 难点 1：怎么让 LLM 稳定吐出结构化三元组
直接让模型「输出三元组」会得到五花八门的格式。这里用 Pydantic + `with_structured_output`：

```python
class Triple(BaseModel):
    subject: str; relation: str; object: str
class TripleList(BaseModel):
    triples: List[Triple]

extractor = EXTRACT_PROMPT | get_llm(temperature=0).with_structured_output(TripleList)
```

模型被强制按 schema 返回，拿到的就是合法 `Triple` 对象，无需手写解析与容错。

### 难点 2：抽取失败不能拖垮全流程
逐 chunk 抽取时用 `try/except` 兜底——某个 chunk 抽取失败只是少几条边，不影响整图构建。这是批处理 LLM 任务的通用工程习惯。

### 难点 3：实体定位
原型用最朴素的「实体名是否出现在问题里」匹配。这是刻意为之的**教学简化**，让你看清主干。生产里这一步应换成 LLM 抽取问题实体或 NER，并做实体对齐（「负责人」=「部门负责人」）。文档里明确标注了这个简化点，面试时主动提出改进方向是加分项。

## 五、面试怎么考

- **「GraphRAG 和普通 RAG 区别？什么时候用？」** → 普通 RAG 按语义相似检索片段，GraphRAG 按实体关系在图上检索。当问题需要多跳/聚合关系（"X 关联的所有 Y"）时用 GraphRAG，简单事实问答用普通 RAG 更轻量。
- **「知识图谱怎么从文档建出来？」** → LLM 结构化抽取三元组（实体+关系），实体对齐去重，组装成图。难点在实体消歧和关系规范化。
- **「这套有什么局限？」** → 抽取质量依赖 LLM、成本高（每个 chunk 一次调用）、实体对齐难。实务中常和向量 RAG **混合**：向量召回片段、图召回关系，二者互补。
