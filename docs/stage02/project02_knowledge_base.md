# 项目 2：企业级智能知识库问答系统

> 这是几乎每家公司都在做的需求：把内部文档（员工手册、产品 FAQ、规章制度）变成一个「问它就答、答得有据」的机器人。做完这个项目，你就掌握了 RAG 在真实业务里的完整落地姿势。
>
> 代码目录：`stage02_rag/project02_knowledge_base/`

---

## 一、需求与方案设计

### 业务目标
员工/客户用自然语言提问，系统从企业知识库中找到依据并生成答案，**必须附出处、不许编造**。

### 为什么用 RAG 而不是直接问大模型？
- 大模型不知道你公司的内部规定（它的训练数据里没有）。
- 把文档塞进 Prompt？文档几百页，远超上下文窗口，且贵。
- 微调？成本高、更新慢，文档一改就得重训。

**RAG 是最优解**：文档存向量库，提问时只检索最相关的几段喂给模型。文档更新只需重新灌库，分钟级生效。

### 架构设计（离线建库 + 在线问答）

```
┌─────────── 离线（文档更新时跑一次） ───────────┐
│  data/*.md → 加载 → 切分 → Embedding → Chroma 持久化  │   ingest.py
└────────────────────────────────────────────────┘
┌─────────── 在线（每次提问） ──────────────────┐
│  问题 → 向量检索 Top-K → 拼进 Prompt → LLM → 答案+出处 │   qa.py / api.py
└────────────────────────────────────────────────┘
```

这个划分很关键：**建库慢、检索快**，分开后服务启动只需加载现成向量库，毫秒级响应。

### 关键技术选型

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 向量库 | Chroma（持久化） | 本地零部署，`persist_directory` 一行落盘，学习/中小项目够用 |
| Embedding | bge-large-zh | 中文检索一线效果，经 `common/embeddings_provider` 自动选型 |
| 切分 | Recursive，size=300/overlap=50 | 中文段落适中，overlap 防语义截断 |
| 防幻觉 | System Prompt 强约束 + 出处引用 | 「找不到就说找不到」+ 列出引用资料，可追溯 |
| 温度 | 0 | 知识问答要稳定可复现 |

## 二、实现详解

项目拆成四个文件，职责单一、互相复用：

| 文件 | 职责 | 复用关系 |
|------|------|---------|
| `config.py` | 集中管理路径与超参（chunk_size/top_k…） | 被其余三者 import |
| `ingest.py` | 离线建库 | 独立运行一次 |
| `qa.py` | 问答业务逻辑（建链 + answer 函数） | 被 CLI 和 API 共用 |
| `api.py` | FastAPI 暴露 HTTP 接口 | import qa |

### 难点 1：怎么让答案「有据可查」
核心在 `qa.py` 的 System Prompt 和返回结构。我们不只返回 `answer`，还把 `result["context"]`（检索到的原文片段）一并返回为 `sources`。前端就能展示「这句话来自手册第几节」——这是 RAG 产品取信用户的关键，也是和「裸大模型」的本质区别。

### 难点 2：怎么防止模型不懂装懂
靠 Prompt 里的硬约束：

```
1. 只能依据【参考资料】回答，不得使用外部知识。
2. 不足以回答时，明确说「未找到」。
```

配合 `temperature=0`，模型在没检索到内容时会老实说找不到，而不是幻觉一个答案。代码里专门留了一个「问知识库里不存在的问题」的测试用例验证这一点（见 `01_minimal_rag.py` 第三问）。

### 难点 3：服务怎么不每次请求都重建链
`api.py` 用 `@app.on_event("startup")` 在启动时建好 RAG 链常驻内存，请求只走「检索+生成」。这是 LLM 服务最基础也最常被忽略的性能习惯。

## 三、运行步骤

```bash
# 0. 装依赖、配 .env（填一个 API Key）
pip install -r requirements.txt

# 1. 建库（文档更新时才需重跑）
python stage02_rag/project02_knowledge_base/ingest.py

# 2a. 命令行问答
python stage02_rag/project02_knowledge_base/qa.py

# 2b. 或启动 API 服务，浏览器开 http://127.0.0.1:8000/docs 调试
python stage02_rag/project02_knowledge_base/api.py
```

把 `data/` 换成你自己的文档，重跑 ingest，就是你自己公司的知识库助手。

## 四、复盘与进阶

做完基础版，按下面的顺序加强，每加一项都用 `03_rag_eval.py` 量化效果：

1. **召回不准** → 上 [混合检索](02-07_search_strategies.md)（向量 + BM25），专有名词/编号召回立刻变好。
2. **召回有噪声** → 加 [Re-rank](02-11_rerank.md)，先粗召回 k=8 再精排到 4。
3. **问法刁钻** → 上 [MultiQuery](02-10_multiquery_ragfusion.md) 扩召回。
4. **不知道好坏** → 用 [评测集](02-12_rag_evaluation.md) 把命中率/忠实度跑成数字。

## 五、面试怎么考

- **「你这个 RAG 怎么防幻觉？」** → Prompt 强约束（只依据 context、找不到就说找不到）+ 出处引用可追溯 + temperature=0。光说「Prompt 写好点」会被认为不专业。
- **「chunk_size 怎么定的？」** → 没有银弹，要用评测集试。太大噪声多、太小语义碎；中文一般 200-500，配 10-20% overlap 防截断。强调「我是用命中率调出来的，不是拍脑袋」。
- **「向量检索召回不全怎么办？」** → 混合检索补关键词、MultiQuery 扩问法、Re-rank 提精度，三板斧。
- **「文档更新了怎么办？」** → 离线增量重灌库，在线服务不停。能讲清「离线建库/在线检索」的架构划分是加分项。
