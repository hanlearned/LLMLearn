## 一、需求与方案设计

### 痛点
团队里调 Prompt，全靠主观感觉，不可信、不可复现、无法回归。换了个人、过了一周，就说不清「到底哪版好、好多少」。

### 方案：把 Prompt 当代码一样做 A/B 测试
固定测试集 → 两版 Prompt 各自作答 → LLM 裁判成对比较 → 统计胜率。三个工程要点缺一不可：

| 要点 | 为什么 |
|------|--------|
| **固定测试集** | 控制变量。同一批问题才能横向比较 |
| **成对比较（pairwise）** | 裁判「二选一」比「分别打 1-10 分」更稳、更准 |
| **位置去偏** | LLM 裁判有「偏爱第一个」的位置偏见；交换 A/B 顺序各评一次抵消它 |

---

## 二、实现详解

### 难点 1：为什么用成对比较而不是各自打分
让 LLM 给单个回答打绝对分（7 分还是 8 分？）非常不稳定。但让它在两个回答里挑一个更好的，判断力强得多。这是 LLM-as-a-Judge 的重要经验：**能用比较就别用打分**。

### 难点 2：位置偏见与去偏
研究和实践都表明，LLM 裁判倾向于选**位置靠前**的那个。解法是「双向评判」：

```python
v1 = judge_pairwise(q, ans_a, ans_b)   # A 在前
v2 = judge_pairwise(q, ans_b, ans_a)   # B 在前（位置交换）
# 只有两次都赢，才算真的赢
```

一个回答只有在「不管放前放后都被选中」时才算本题获胜，否则算平局。这样裁判的位置偏见就被抵消了。

### 难点 3：稳健解析裁判输出
裁判被要求只输出 `1`/`2`/`tie`，代码再做容错解析。温度设 0 让裁判判断可复现。

## 四、复盘与进阶
1. **测试集建设**：从线上真实问题里采样、覆盖边界 case，是平台价值的根基。
2. **多版本 & 趋势**：支持 N 版 Prompt 循环赛，胜率落库做成趋势看板。
3. **多维度评判**：不只「整体更好」，拆成准确性/有用性/安全性分别评判。
4. **接入 LangSmith**：用其内置的 evaluation 能力做大规模自动化评测。

## 五、面试怎么考
- **「怎么评估 Prompt/模型效果？」** → 固定测试集 + LLM-as-a-Judge 成对比较 + 位置去偏 + 胜率统计。强调「可复现、可回归」。
- **「LLM 当裁判可靠吗？有什么坑？」** → 有位置偏见、长度偏见（偏爱长答案）、自我偏好（偏爱同源模型）。缓解：成对比较、位置交换、必要时人工抽检校准。
- **「为什么成对比较优于打分？」** → 绝对打分方差大、校准难；相对比较更符合 LLM 的判别能力。
